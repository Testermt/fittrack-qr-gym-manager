# FitTrack Security Audit — Firestore / Client Architecture

**Scope:** `firestore.rules`, `member.js`, `admin.js`, `admin.html`, `index.html`, `firebase-config.js`
**Posture:** No Firebase Auth for members (fully anonymous/unauthenticated client). Admin uses Google Sign-In + `admins/{email}` allowlist + reauth-for-sensitive-actions. All trust boundaries live in `firestore.rules` — there is no server (no Cloud Functions in this stack).

That last point is the headline finding: **your only line of defense is the rules file**, and anyone can open DevTools on your live site, grab the already-initialized `firebase` app object, and issue raw Firestore SDK calls with the exact same privileges as your UI. The public API key in `firebase-config.js` is *not* itself a vulnerability (Firebase API keys are meant to be public) — but it means client-side JS logic (GPS checks, "already registered" checks, button disabling) provides **zero** security. Only what's in `firestore.rules` counts.

---

## 1. GPS Geofencing Bypass — CONFIRMED, TRIVIAL

**Root cause:** `checkins/{checkinId}` create rule (lines 59-67) never references location data at all. GPS is calculated entirely client-side in `calculateDistance()` (member.js) purely for UX. The rule only checks field shape + that the target member is `approved`.

**Proof of concept** (run in browser console on your own site, no location permission needed):
```js
const db = firebase.firestore();
db.collection("checkins").doc("9876543210_2026-09-11").set({
  memberId: "9876543210",
  phone: "9876543210",
  dateKey: "2026-09-11",
  timestamp: firebase.firestore.FieldValue.serverTimestamp(),
  method: "geofenced-gps"
});
```
This succeeds from anywhere on Earth, for any member whose phone number you know, with zero GPS involved. Browser mock-location extensions aren't even necessary — you skip the browser entirely.

**Why this is hard to "patch" with rules alone:** Firestore Security Rules cannot see device GPS — they only see whatever the client *claims* in the write payload, which is exactly what's compromised. Any rule like `request.resource.data.lat` would just move the forgeable field around.

**Real fixes (ranked by effectiveness):**
- **Best:** Move check-in writes into a Cloud Function (`onCall`), require **Firebase App Check** (reCAPTCHA Enterprise / Play Integrity / DeviceCheck) on the callable, and have the function itself do whatever validation is possible server-side. This doesn't prove GPS truthfulness either (App Check proves *this is your real app*, not *this GPS is real*), but it kills console/REST/script attacks entirely, which is 95% of your realistic threat model.
- **Actually solves geofencing:** Replace GPS trust with **proof of physical presence** — a rotating QR/NFC code generated by a device physically at the front desk (e.g., regenerated every 60 seconds, signed, single-use). Members scan it in person; the code itself becomes the write-authorization token, checked server-side. GPS is spoofable by any teenager with a location-mock app; a rotating in-person code isn't.
- **Cheap partial mitigation:** Enable **App Check enforcement** on Firestore for the `checkins` collection today. It won't stop a determined attacker with your app's real DevTools open, but it stops casual REST-API/script abuse immediately.

## 2. Privilege Escalation on `approved` / `paymentStatus` — NOT EXPLOITABLE (good)

I tried to break this and couldn't, via the rules as written:
- Public `create` forces `approved == false` and `paymentStatus == "pending"` — enforced server-side, `hasOnly()` blocks smuggling extra fields.
- `update`/`delete` on `members/{phone}` require `isVerifiedAdminDirect()` — a self-registered "member" has no `request.auth` at all (no sign-in flow exists for them), so they structurally cannot hit the admin branch.
- Deleting and re-creating your own doc doesn't help — the public branch still forces `approved:false`.

This part of your architecture is sound. Good use of `hasOnly()` and split create-branches.

## 3. Backdating / Future-dating Check-ins — CONFIRMED (contradicts your stated intent)

You stated the rules "restrict writes so members... cannot forge check-ins for future dates." **They don't.** Line 62-63 only regex-validates `dateKey` as `YYYY-MM-DD` format — it never compares it to `request.time`. `timestamp == request.time` only pins the *timestamp* field to server time; `dateKey` is fully client-chosen.

**PoC:**
```js
db.collection("checkins").doc("9876543210_2030-01-01").set({
  memberId: "9876543210", phone: "9876543210",
  dateKey: "2030-01-01",
  timestamp: firebase.firestore.FieldValue.serverTimestamp(),
  method: "manual"
});
```
This creates a valid-looking future check-in today. Same trick backdates attendance for any past date, one doc per date (bounded only by the deterministic-ID collision), which could be used to fabricate an attendance history (e.g., a member disputing a "membership frozen for non-attendance" policy, or gaming a streak/loyalty feature).

**Fix:** Rules language can't cleanly parse a `YYYY-MM-DD` string against `request.time`'s calendar date (no date-decomposition functions). The clean fix is architectural: **don't let the client set `dateKey` or the document ID at all.** Route check-ins through a Cloud Function that derives `dateKey` from `request.time` server-side, or at minimum store `timestamp` only and derive the "day" bucket via a scheduled/triggered Cloud Function reconciliation. Rules-only band-aid (weaker, but better than nothing) — reject anything but an auto-ID and validate a tight timestamp window server can't be spoofed:
```
allow create: if request.resource.data.timestamp == request.time
              && ... // dateKey removed from client-writable schema entirely
```
and compute `dateKey` in a Cloud Function `onCreate` trigger instead of trusting the client's copy.

## 4. Flooding / Cost-Exhaustion DoS — CONFIRMED

Nothing rate-limits `checkins` or `members` creation. An attacker who knows (or brute-forces — see #5) a handful of approved phone numbers can script:
```js
for (let d = 0; d < 3650; d++) {
  const date = /* format date d days out */;
  db.collection("checkins").doc(`9876543210_${date}`).set({...});
}
```
— thousands of writes in seconds, each billable, permanently bloating the collection and the admin dashboard's history views. Separately, the public `members` create endpoint has no CAPTCHA/App Check, so a script can flood the admin's approval queue with junk pending registrations (each needing a phone-number-shaped ID, easy to generate in bulk).

**Fix:** App Check enforcement (blocks non-browser/scripted callers using stolen config), plus Cloud Functions with per-IP/per-identity throttling if you want real rate limits — Security Rules alone have no concept of "requests per minute."

## 5. Phone Number / PII Enumeration — CONFIRMED, and probably your most sensitive real-world exposure

`allow get: if true;` on `members/{phone}` means **anyone who guesses a valid document ID gets the full document** — `name`, `address`, `plan`, `paymentStatus`, `approved`. Indian mobile numbers occupy a well-known, narrow range (10 digits starting 6–9). A script can iterate that space (or a targeted subset, e.g. a known area-code/carrier block) and call:
```js
for (const phone of candidatePhones) {
  db.collection("members").doc(phone).get().then(doc => {
    if (doc.exists) console.log(doc.data()); // name + home address, unauthenticated
  });
}
```
`allow list` is admin-only (good — that stops a single query dumping everyone), but repeated `get()` calls achieve the same result more slowly. This leaks **name + home address** tied to a real phone number to anyone willing to run a loop — a genuine PII/safety concern, not just a nuisance.

**Fix:** Split the document. Keep `name`/`address` in a private doc admins can read, and expose only a minimal public-safe status doc (`approved`, `paymentStatus`, `expiryDate`, `planLabel`) for the "Check Status" feature — maintained via a Cloud Function trigger that mirrors the safe subset whenever the private doc changes. This also lets you finally enable App Check + rate limiting on the *status* endpoint without breaking legitimate UX.

## 6. Unvalidated `expiryDate` on Self-Registration — LOW severity, worth fixing

`hasValidMemberShape()` only checks `expiryDate is string` — it never verifies it's actually `joinDate + plan.months`. A self-registering attacker can submit `expiryDate: "2099-01-01"` directly. Today this has limited blast radius (check-in only gates on `approved`, not `expiryDate`), but it's a latent landmine if you ever add expiry-based logic (auto-suspend, "active" badges trusted elsewhere) without server-side recomputation.

**Fix:** Store `joinDate`/`expiryDate` as Firestore `Timestamp` (not strings) and validate `expiryDate` falls in an admin-defined bound relative to `request.time`, or better, recompute it server-side in a Cloud Function on create and ignore/overwrite the client's value.

---

## 7. Bonus bug (not a vulnerability, but you should know): member check-in history is currently broken

`checkins` rule line 69 restricts *all* reads (`get` and `list`) to `isVerifiedAdminDirect()`. But `member.js`'s `loadMemberCheckinHistory()` runs an unauthenticated `.where("memberId","==",...)` query for the member's own status page. As written, that query should be **denied by your own rules** for every non-admin — meaning regular members likely see "Could not load check-in history" in production right now (silently swallowed by your try/catch). This doesn't need "fixing" for security — if anything, loosening it re-opens enumeration risk (§5) — but you should decide intentionally rather than have it fail silently.

## Priority Action List
1. **Enable Firebase App Check** on the whole project today — cheapest, highest-leverage single change; kills nearly all scripted/REST abuse (#1, #4, partially #5).
2. **Split `members` into public-safe status doc + private PII doc** — fixes the phone-enumeration PII leak (#5) properly, not just with App Check band-aid.
3. **Move check-in writes to a Cloud Function** — the only real fix for #3, and lets you add per-member/per-day transactional locking and throttling for #4.
4. **Replace/augment GPS with a rotating in-person QR/NFC token** if you actually care about proof-of-presence (#1) — GPS from a browser is fundamentally unspoofable-proof, no rule can fix that.
5. Recompute `expiryDate` server-side rather than trusting client math (#6).

Everything above was verified directly against your uploaded `firestore.rules`, not assumed.
